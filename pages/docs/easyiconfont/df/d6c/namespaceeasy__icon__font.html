Detailed Description

easy_icon_font.py

Backend for the Easy Icon Font plugin's toolbar tool. Builds icon fonts
from vector SVG paths, and registers raster (PNG/WEBP/etc) icons that
don't vectorize as plain textures instead - one registry, one CSV export,
one DataTable, covering both.

REQUIREMENTS
------------
`fontTools` must be installed into UE's *bundled* Python interpreter, not
your system Python - the editor's embedded Python is what actually runs
this:

    "<EngineInstallDir>\\Engine\\Binaries\\ThirdParty\\Python3\\Win64\\python.exe" -m pip install fonttools numpy scikit-image Pillow

Restart the editor after installing.

IMPORTANT - YOUR FONT FILE
---------------------------
The plugin ships a blank starter font at Resources/EasyIconFont.ttf so
the default "Font file" path in the toolbar window works out of the
box on a fresh install. Once you've added real icons to it, that file
is YOUR project's actual data - future plugin updates (new .zip drops,
git pulls, etc.) should NOT overwrite it. If you're applying updates by
extracting a zip over the existing Plugins/EasyIconFont folder, either
skip Resources/EasyIconFont.ttf specifically, or point the "Font file"
field at a font living outside the plugin folder entirely (e.g.
somewhere under your own project's Content or a Saved/staging folder)
so it's never at risk from a plugin-folder overwrite. The
.codepoints.json registry sidecar living next to it is separate from
this concern (it's generated by this script, never shipped in a
plugin update), but if the .ttf and the registry ever drift out of
sync - e.g. the .ttf gets reset while the registry still lists icons
that used to be in it - the fix is just re-adding those icons through
the tool again; get_or_assign_codepoint reuses each glyph's original
codepoint from the registry, so already-built DataTables/widgets don't
need to change.

WHAT'S IMPLEMENTED
-------------------
- MonoVector: single flat-fill SVG -> a real glyph outline (glyf table),
  same technique as the original svg_to_font.py. Infinitely scalable,
  tinted by the TextBlock's own color at runtime.
- ColorVector: flat, limited-palette RASTER source (PNG/WEBP/etc) -> a
  COLR/CPAL glyph. Quantizes to a small palette, segments by color,
  traces each region's boundary, stacks the results as layers. Requires
  numpy + scikit-image in addition to fontTools/Pillow (see
  add_color_glyph_to_font's docstring). NOT implemented for SVG sources
  yet -- an SVG-native path (grouping existing paths by fill color
  instead of quantize-and-trace) would be a separate, likely simpler,
  follow-up.
- Texture: any raster image -> imported as a plain UTexture2D and
  registered as a Texture-type row. No font involved.

CAVEATS
-------
- ColorVector is raster-only for now (see WHAT'S IMPLEMENTED above).
- ColorVector layers are painted in most-populous-color-first order,
  not necessarily the source image's actual visual z-order (what's
  drawn on top of what). This happens to match for icons where the
  biggest-area color is meant to sit at the back (most badge/ring/star
  style icons), but could paint a layer in the wrong order for an icon
  where a small color region is supposed to sit BEHIND a larger one.

USAGE (called by the plugin's toolbar tool, or directly from UE's Python
console):

    import easy_icon_font

    # single entry point the toolbar window actually calls:
    easy_icon_font.add_icon_and_reimport(
        source_path=r"C:\\path\\to\\icon_bell.svg",
        font_path=r"C:\\path\\to\\Project\\Content\\Icons\\Fonts\\MyIcons.ttf",
        font_asset_path="/Game/Icons/Fonts/MyIcons",
        glyph_name="icon_bell",
        glyph_type="auto",              # or "MonoVector" / "Texture"
        project_texture_dir="/Game/Icons/Textures",  # only used for Texture rows
    )

    # check what's registered:
    easy_icon_font.list_registered_glyphs(r"C:\\path\\to\\...\\MyIcons.ttf")

protected 
Builds one TTGlyphPen glyph from a list of (x, y)-point contours
in image pixel space, using a shared scale/offset so every color
layer of the same icon lines up pixel-for-pixel. Contours become
straight-line polygons (no bezier fitting) -- plenty smooth at
normal icon sizes once traced from a reasonably anti-aliased source
and simplified, same as any polygon-approximated raster trace.

Returns (glyph, left_side_bearing). The left_side_bearing MUST be
read from this function's own transformed points, not left at 0 or
read from glyph.xMin -- TTGlyphPen-built glyphs don't have xMin
populated until compile() time (same gotcha documented on
build_glyph_from_svg, the mono-glyph equivalent of this function).
Getting this wrong doesn't corrupt the outline itself -- it's still
the right shape -- but every layer with a different true xMin ends
up horizontally offset from every other layer by a different wrong
amount when actually rendered (hmtx's left side bearing is what
positions a glyph's outline horizontally; leaving it at 0 for every
layer ignores that each layer's outline sits at a different true x
position). That's exactly the "each color layer offset from the
others" bug this was written to fix.

protected 
Collapses near-duplicate colors left over from quantizing an
anti-aliased source: PIL's median-cut quantizer can spend separate
palette slots on colors that are visually identical but differ by a
few RGB values (edge-blend pixels between two flat regions), rather

toward. Greedily merges any color within distance_threshold of a
more-populous, not-yet-merged color into it, remapping those pixels
in quantized_rgb. Returns (updated quantized_rgb, reduced colors
list, ordered most-to-least populous).

_quantize_image_colors ( source_image,
max_colors = 8 )
protected 
Returns (quantized_rgb, opaque_mask, colors) for source_image (a
PIL RGBA Image): quantized_rgb is an (H, W, 3) uint8 array where
every opaque pixel has been snapped to one of at most max_colors
palette colors (via PIL's median-cut quantizer, run only over the
OPAQUE pixels so background transparency can't dilute the palette
with wasted slots), with near-duplicate colors further collapsed by
_merge_similar_colors -- median-cut alone tends to spend a couple of
its palette slots on anti-aliased edge-blend pixels rather than
folding them into the flat color they're actually blending toward.
opaque_mask is the (H, W) boolean mask of which pixels count; colors
is the reduced list of distinct (R, G, B) tuples actually used,
ordered most-to-least populous.

◆ _trace_color_region_to_contours()

_trace_color_region_to_contours ( quantized_rgb,
opaque_mask,
color,
trace_resolution = 256,
dilate_px = 2 )
protected 
Returns a list of contours (each a list of (x, y) points, in the
ORIGINAL image's pixel coordinate space) outlining every region
where quantized_rgb == color within opaque_mask. Traces at a
downsampled resolution (trace_resolution on the longer side) to keep
point counts sane, then simplifies further with Douglas-Peucker
before scaling back up -- native-resolution tracing produces far
more points than an icon glyph needs.

Winding direction is trusted as-is from skimage.measure.find_contours
and this IS correct for hole-bearing regions (a ring/donut-shaped
color area) -- verified directly against a ring icon: marching
squares orients every contour consistently, so a hole's contour
comes out wound opposite to its enclosing region automatically,
matching the nonzero-winding-rule property TrueType glyf needs.

dilate_px grows the mask slightly (in the DOWNSAMPLED mask's pixel
space) before tracing. This matters because each color is traced
independently -- two adjacent colors sharing a boundary each get
that boundary simplified (Douglas-Peucker) separately, and the two
independent simplifications don't always agree on exactly the same
vertices along that shared edge. Left undilated, that mismatch shows
up as a thin sliver of background peeking through at every
color-to-color seam (visible as e.g. a crescent gap in a ring, or a
ghost outline next to a star sitting on a differently-colored
field). Growing every layer slightly makes them OVERLAP instead of
almost-meet -- and since COLR layers paint over each other in order,
an overlap is invisible (the later layer just covers it) while a gap
is not. Set to 0 to disable if you'd rather see the raw tracing.

Builds a ColorVector (COLR/CPAL) glyph from a flat, limited
-palette RASTER source (PNG/WEBP/etc): quantizes to at most
max_colors, segments into per-color regions, traces each region's
boundary, and stacks the results as COLR layers against a shared
CPAL palette (extended, not replaced, if this font already has
ColorVector icons in it -- multiple icons share one palette rather
than each fragmenting their own).

Not for genuinely photographic/gradient art -- see the module
docstring. Not for SVG sources either: SVG multi-fill icons already
HAVE real vector path data per color, so tracing them as if they
were raster would throw that away for no benefit -- that's a
separate, not-yet-built code path (would reuse
_split_into_subpath_pens/_fix_evenodd_winding grouped by fill color
instead of this function's quantize-and-trace approach).

Requires numpy and scikit-image in addition to fontTools and
Pillow. Install into UE's bundled Python interpreter the same way
as fontTools:
    <EngineInstallDir>...\\python.exe -m pip install numpy scikit-image

add_icon_and_reimport ( source_path,
font_path,

glyph_name,

project_texture_dir = None,
csv_export_path = None,

Single entry point the Easy Icon Font toolbar window calls.

glyph_type: "auto" | "MonoVector" | "ColorVector" | "Texture"
  "auto" routes by file extension: .svg -> MonoVector. Anything else
  (PNG/WEBP/etc) -> attempts ColorVector first, and falls back to
  Texture only if that attempt raises (missing numpy/scikit-image,
  a fully-transparent image, no traceable color regions, etc). This
  does NOT check whether the source is actually flat-color/suitable
  for vectorization -- a photographic or gradient-heavy PNG will
  happily "succeed" as a blocky, ugly ColorVector rather than being
  recognized as unsuitable and routed to Texture. If that happens,
  just re-add the same icon with glyph_type="Texture" explicitly to
  override auto's choice.

  Explicitly requesting glyph_type="ColorVector" does NOT fall back
  on failure -- it raises, same as before. The fallback only applies
  to "auto", so an explicit request failing is something you find
  out about immediately rather than silently getting a texture
  instead of the color-vector you asked for.

datatable_asset_path: optional. If given, reimports that EXISTING
DataTable asset from the freshly-exported CSV as the last step (see
reimport_datatable_from_csv) -- the DataTable must already exist,
this doesn't create one. Left as None to skip that step entirely,
same as before this parameter existed.

e.g. "/Game/Icons/DT_EasyIcons") directly from csv_path's contents,
so the DataTable stays in sync automatically every time an icon is
added - no more manual right-click > Reimport after every export.

The DataTable must already exist, created once by hand via the
normal Content Browser "Import as DataTable" flow (row struct
FIconGlyphRow) against any earlier CSV export - this only refreshes
an existing asset's rows, it doesn't create the asset from scratch.
Must run inside the UE editor's Python environment.

Uses DataTableFunctionLibrary.fill_data_table_from_csv_string,
UE's own purpose-built API for exactly this (repopulating an
existing DataTable's rows from CSV text) -- NOT AssetImportTask,
which an earlier version of this function used and which turned
out not to reliably reimport a DataTable in practice (it has no
dependable way to infer "use FIconGlyphRow" without a lot of extra
factory configuration this project doesn't need). Reading the file
ourselves and calling this directly sidesteps that whole guessing
game -- the DataTable keeps using whatever row struct it already
has, and this just replaces its row contents.

◆ remove_icon()

remove_icon ( font_path,
glyph_name,
csv_export_path = None ) 
Removes glyph_name from the registry, and - for MonoVector/
ColorVector rows - from the font itself: cmap entry, glyf outline(s),
hmtx metric(s), and glyph order. For ColorVector this also removes
every layer glyph (icon_name.layer0, .layer1, ...) and the base
glyph's entry in the COLR table. CPAL palette slots that were only
used by this icon become unused but are NOT removed or renumbered -
doing that safely would mean rewriting every OTHER ColorVector
icon's colorID references in the same font, which isn't worth the
complexity for palette entries that cost a few bytes each and
aren't visible anywhere. Harmless, just slightly wasteful.

For a Texture row, only the registry entry is removed - the actual
UTexture2D asset is left alone. Deleting a project asset out from
under the user as a side effect of a font-registry operation is the
kind of surprise this deliberately avoids; if you want the texture
asset gone too, delete it yourself in the Content Browser.

Raises ValueError if glyph_name isn't registered. Must run inside
the UE editor's Python environment if font_asset_path-style
reimporting is wanted afterward - this function itself doesn't
reimport anything, same division of responsibility as
add_svg_glyph_to_font vs add_svg_and_reimport (call
reimport_font_face_asset yourself after, if needed).

◆ run_setup()

run_setup ( status_path = None) 
Everything the toolbar window's Setup button does in one call:
installs missing Python packages (see install_missing_dependencies),
then ensures Resources/EasyIconFont.ttf exists, creating it from
the blank template on a fresh install (see
ensure_default_font_exists), then points the plugin's bundled
EasyIconFontFace asset at that file. Re-checks dependency status
afterward and writes it to status_path, same as
install_missing_dependencies alone did before this existed.

Each of these three steps is independent -- one failing is logged
but doesn't stop the others from running, so e.g. a missing
EasyIconFontFace asset doesn't prevent dependency status from being
reported.

Fixing up EasyIconFontFace's source path matters because that
asset ships bundled with the plugin, and its recorded source path
is whatever absolute path was true in the project it was ORIGINALLY
created in -- meaningless the moment the plugin is used somewhere
else, exactly like Resources/EasyIconFont.ttf not shipping was
meant to solve for the font file itself. reimport_font_face_asset
already falls back to this project's own font when the recorded
path doesn't resolve (see _reimport_single_font_face), so calling
it here just means that correction happens automatically as part of
Setup, rather than only the first time someone happens to click Add
Icon and hits the fallback indirectly.
